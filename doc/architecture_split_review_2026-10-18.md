## 需要修改完善的地方

### A1：蓝图核心仍反向依赖 Actor，违反明确的单向依赖契约

证据：`blueprint/src/blueprint_place.gd:7` 引用画布侧 `blueprint_codec.gd`；第 15、17、18 行引用 InkItem、Nail、GearCenters。`placement_error()` 和 `place()` 也直接访问 Canvas、Surface 和历史。

与 `actor/canvas/blueprint/doc/架构.md` 的“`blueprint/src` 不得 preload actor/ui”直接冲突。目录层面形成核心 → 画布蓝图 → 核心的双向依赖；这不等于已经发现脚本加载死循环，但足以否定“核心已完全独立”的结论。

**建议：按真实职责调整归属。** 把现有放置事务作为画布适配实现放回 `actor/canvas/blueprint/src/`，核心保留格式、校验、存储等独立数据能力。现有 codec 已依赖画布坐标与实体，不建议为了迁移进核心再引入一套庞大的接口。同步修订蓝图架构目标图，不能同时宣称“核心不依赖 Actor”和“核心放置可以依赖 codec”。

边界：这里只搬外围实现和引用，原有墨量预检、连接重建、失败不扣料及一次放置一次撤销的算法保持原样；不动 `.inkbp` 格式和 `ink/` 实现。

验收：核心没有 Actor/UI 直接资源依赖；蓝图原有采集、放置、撤销、重做、连接独立和重进测试通过。

### A2：编辑器视图仍直接操作画布，不满足“视图只提交动作”

证据：`debug/creative/ui/src/editor_palette.gd:52` 持有 `_map_canvas`；第 188 行寻找画布内部 `brush_panel/PenSlider`，第 197 行直接调用 `set_brush_size()`；第 232 行把按钮绑定到画布私有 `_on_nail_visibility_toggled()`，另有直接调用 `select_ink()`。

因此，虽然已有 `action_requested`，视图仍同时承担控件展示、文档/工具动作和另一套控件的同步。

**建议：沿用已有动作信号，把笔宽、颜色选择、钉子显示切换交给装配端执行。** 视图只接收显示值并更新自身；显示查询可使用已有 Callable 方式。先移除直接写入与私有方法调用，再逐步移除画布内部节点路径，不新增通用消息总线。

验收：操作行为保持一致；视图不调用 Canvas/Surface 的修改方法，不连接其私有处理函数；点击和滑动不会穿透到世界输入。

### A3：Creative 仍是行为集中点，session 的拆分尚未带走多数交互行为

读取时 `creative.gd` 约 3,100 行，`canvas.gd` 约 1,230 行，`canvas_surface.gd` 约 1,990 行。行数不是失败依据，以下职责混合才是：

- Creative 仍创建对话输入窗口、地图文字窗口、复活区域窗口，执行相应实体增删。
- 小怪查找/创建已经提取，但缩放、拖动、视图锁定和记录变换仍集中在 Creative。
- 图片容器、图片恢复/删除以及若干布局对象事务仍在同一个主脚本。
- `editor_commands.gd` 的 REQUIRED_PORTS 仍大量指向 Creative 私有方法；不能把回调转发视为对应功能已经独立。

**建议按原迁移计划继续完成现有切片：** 先补全 monster_tools 的缩放/拖动；再提取 dialogue_tools、map_text_tools、image_tools。窗口布局放 `debug/creative/ui/`，工具负责领域操作，Creative 保留输入分发、装配、进出编辑器和协调历史。复用现有 session 与唯一时间线，不新建多个 Controller/Manager。

画布暂只继续整理工具栏、显示与输入分发；本轮不拆改笔刷、墨水层、固化和破坏算法。不能为了把文件压到某个行数，将机制代码机械切碎。

验收：一个动作仍对应一个撤销事务；切工具、窗口失焦、切关均可取消拖动；不增加第二套撤销栈。每片改动独立验证，目录迁移不夹带行为调整。

### A4：正式运行对象仍放在 debug/creative，调试与成品运行边界未分清

证据：`debug/creative/src/map_dialogue_trigger.gd` 在游玩时运行玩家检测与触发逻辑；扉页、第一页、Peak 等正式地图直接引用该脚本。`map_imported_image.gd` 承担保存到地图后的图片/GIF 显示，不只是导入窗口或编辑辅助。

**建议：运行部分按地图内容归到 `map/` 的运行脚本位置，编辑窗口、选框、导入操作保留在 Creative。** 优先移动现有脚本、保留 UID、更新场景引用，不为迁就目录规则凭空增加 Actor 包装。以后确实作为独立 Actor 维护时，再提供真实入口场景。

验收：正式地图不依赖 debug 目录中的对话触发/图片播放实现；禁用编辑界面后仍可触发对话、显示图片和动画；重开地图与导出包资源引用有效。

### A5：传送门依赖选关 UI，关卡规则未独立

证据：`actor/portal/src/map_portal.gd:6` preload `ui/level_select/src/level_select.gd`，用它校验目标和取得下一关。选关脚本同时管理按钮、正式路线、磁盘扫描与新建地图。

**建议：将列表发现、目标校验、正式路线这些已有纯逻辑移入 `map/src/level_catalog.gd`，传送门和选关界面共同调用。** UI 保留按钮与反馈，地图创建写盘单独作为明确操作；不引入全局服务注册器。

顺带需要补齐的既有问题：`_scan_map_levels()` 当前仍只接受 `.tscn`，导出后的 `.tscn.remap` 会在预过滤阶段被排除；`find_levels()` 仍先放固定列表（含 Peak），再追加自建地图，不能保证注释所说“Peak 最后”。这两项在本次源码中仍存在；本轮未重做 PCK 复现，不将静态确认表述为新增实机复现。

验收：传送门不再引用 UI 脚本；正式路线、Peak 独立入口、自建地图展示规则明确；包含额外地图的导出包也能发现地图。

### B1：外部仍读取私有编辑状态，迁移兼容层没有收尾

证据：`ui/cursor/src/game_cursor.gd:127` 的 `_uses_ring()` 直接读取 Creative 的 `_monster_mode`、`_dragging_monster`、`_layout_drag_target`；Creative 中仍有这些代理属性。静态采样在 32 个测试文件中找到约 244 处字面形式的 `creative._...`，说明旧接口依赖仍广泛存在；该数字不包含其他变量名或动态访问。

**建议：先迁移生产调用方，再处理旧测试。** 光标只需要“当前应显示画笔还是对象放置指示”的明确状态，不应知道拖动字段。复用现有编辑入口和状态事件；不要为了每个测试再新增一个生产 API。待实际调用归零后删除无用代理，保留仍服务旧地图序列化的兼容入口，避免误删。

验收：生产 UI 不访问 Creative 私有会话字段；剩余兼容项逐项注明真实消费者；测试以可观察结果验证，不把搬函数造成的大量报错当成功能回归。

### B2：保存模块虽然独立，仍通过节点名抓取并修改 Creative

证据：`application/editor_save.gd:75` 的 `pack_playable()` 在第 89 行自行 `get_node_or_null("Creative")`，临时写入该节点的 `editor_draft` 和 `edit_snapshot_path`。

这不是本次已经复现的保存错误，但与模块注释所述“通过 ctx 显式传入对象”的方向不完全一致，保存仍依赖特定场景拓扑与字段。

**建议：由装配调用点明确传入保存所需的草稿承载节点或预先采集的草稿数据，保存端不再反向查找节点。** 保留临时状态的成对恢复，继续保证普通保存不生成、不墨化、不清空历史，不另造大存档模型。

验收：普通保存与 F2 文档回归通过；保存模块可以在不依赖固定 Creative 节点名的夹具中完成相同工作。

### B3：general 已被复用，但仍了解具体角色内部结构

证据：`actor/general/effects/character_death.gd:104` 通过路径包含 `/Arm/` 判断角色部件，第 110 行判断 `BodyBone`；还识别 ShieldArt、BombArt 等具体角色命名。

满足“两种 Actor 使用”，不等于满足 `actor/general/README.md` 中“不依赖具体 Actor 内部路径或实现细节”。

**建议：由 Player/Monster 各自整理部件、遮罩、角色标识后传给共享死亡表现，general 仅处理输入的表现数据。** 不复制两套死亡特效，不改伤害、死亡、复活和墨水规则。

验收：共享特效无需识别具体骨骼路径；玩家、小兵、炸弹狂、盾兵的遮罩、层级与消散效果保持一致。

### B4：UI 命中仍有多份实现，应收敛重复逻辑

证据：Creative 的 `_pointer_over_editor_ui()` 与 BlueprintSystem 的 `_pointer_over_ui()` 都遍历控件并检查裁剪；后者仅接受若干交互控件类型，前者接受范围更广。画布和光标还使用 `gui_get_hovered_control()`。

**旧报告的“蓝图完全不检查父级裁剪”已经过时：当前代码已检查。** 现在的问题是重复实现与不同调用时机，不能把所有判据简单替换成同一个悬停查询。

建议只复用“按当前鼠标事件位置检查可交互控件及祖先裁剪”的小函数，调用方保留自己的模态、工具状态策略；放在现有 UI 输入相关位置即可，不新建全局命中管理器。

验收：同帧移入点击、滚动裁剪、透明布局、模态窗口均正确，画布/布局/蓝图/光标之间不产生穿透或误拦截。

- 不处理容量为零的墨水语义，不改各色机制、原生扩展、引擎旋钮或 DLL，不以消除退出告警为由修改引擎资源管理。
