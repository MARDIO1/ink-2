# AI 工作规范

本项目允许 AI 辅助开发，但代码最终需要由人长期维护。**优先保证简单、明确、可读，而不是展示通用性和“健壮性”。**

## 1. 总原则

- 先理解现有架构，再修改代码。
- 优先修改最少的代码解决问题。
- 不为了“以后可能需要”提前设计复杂抽象。
- 不主动增加兼容层、fallback、通用接口、缓存层或状态机，除非当前需求确实需要。
- 不擅自重构与当前任务无关的代码。
- 如果发现架构问题，先说明，再修改。

## 2. 控制代码规模

禁止为了一个简单功能生成数百行代码。

新增功能前先判断：

> 能否用一个明确的小函数解决？

如果可以，就不要创建新的 Manager、Controller、Helper、Adapter、Context 等抽象。

同一个类职责明显过多时应拆分，但不要为了“单一职责原则”机械拆成大量小文件。

## 3. 注释要求

注释只解释以下内容：

- 不直观的设计原因；
- 必须保持的不变量；
- 容易踩坑的引擎行为；
- 数学、物理或性能上的关键原因。

例如：

```gdscript
# position 对应像素形状左上角，不是质心。
```

不要写：

- 开发历史；
- “以前这里有一个 bug”；
- 长篇性能复盘；
- 对代码逐行翻译；
- 大量 ⚠️、🔥、加粗式说明；
- 为显而易见的代码写注释。

Bug 历史应该进入 Git commit、issue 或开发日志，而不是永久留在源码中。

## 4. 一个函数只做一件事

函数名必须能准确描述其副作用。

例如：

```text
invalidate_gizmo()
```

只能让 gizmo 失效。

它不应该顺便：

```text
重建物理形状
通知父节点
重新生成贴图
修改世界
```

如果需要这些行为，应分别调用：

```text
invalidate_gizmo()
invalidate_shape()
sync_transform()
```

避免“调用一个看似无害的函数，却触发半个系统”。

## 5. Getter 禁止产生重大副作用

读取属性应该尽可能只是读取。

禁止类似：

```text
读取 body
→ 创建 PBody
→ 注册到世界
→ 重建物理
```

对象创建、注册、销毁等行为必须通过明确函数完成：

```text
bake()
attach()
detach()
rebuild()
```

不要隐藏在 getter 中。

## 6. 使用明确类型，不滥用鸭子类型

这是内部项目，不需要为未知第三方代码无限兼容。

优先：

```text
PixelShape2D
PixelBody2D
```

而不是到处：

```text
has_method("build_shape")
has_method("get_shape")
has_method("rebuild")
```

只有确实需要插件式扩展时才使用接口式判断。

## 7. 不重复做同一件事

修改代码前检查调用链。

避免：

```text
A()
→ B()
→ 已经通知世界

A() 后面
→ 又通知一次世界
```

尤其注意：

- rebuild
- cache invalidation
- editor notification
- redraw
- physics registration
- transform synchronization

这些操作不应因为隐藏调用链被重复执行。

## 8. 缓存必须简单且一致

缓存只用于明确的性能热点。

如果规定：

```text
get_shape() = 缓存接口
build_shape() = 真正重新生成
```

那么其他代码必须统一调用 `get_shape()`。

不要一半走缓存，一半绕过去直接调用 `build_shape()`。

缓存失效条件必须明确。

## 9. 热循环中禁止隐藏重计算

特别检查：

```text
_process
_physics_process
_draw
碰撞循环
solver循环
编辑器拖动通知
```

这些位置不得无意中进行：

- 大规模像素遍历；
- rebuild；
- 纹理重新生成；
- 全图搜索；
- 高频对象分配。

需要重计算时优先：

```text
修改 → 标记 dirty
↓
合适时机统一 rebuild 一次
```

## 10. 编辑器层和运行时物理层分离

Godot Node 主要承担：

```text
编辑
配置
可视化
场景保存
```

PBody / 物理核心承担：

```text
运行时物理
```

不要因为编辑器功能把额外 Node、通知或重建逻辑带进物理热循环。

Editor Gizmo、Inspector 辅助等功能尽量与运行时逻辑分离。

## 11. 不做“假健壮”

不要为了理论上的异常输入加入大量实际不会发生的分支。

例如项目架构已经保证：

```text
PixelBody2D 必须位于 PixelWorld 下
```

那么优先依赖这个约束。

不要每个函数都写一遍复杂 fallback，最终让真正的错误被静默吞掉。

违反项目不变量时，宁可：

```text
assert
push_error
明确失败
```

也不要悄悄生成一个“勉强能用”的替代对象。

## 12. 不为了测试改变架构语义

测试用于验证设计，不应迫使生产代码加入奇怪入口。

如果测试只能通过调用隐藏实现细节完成，应优先修改测试方式，而不是让生产 API 变复杂。

## 13. Godot 代码风格

优先使用：

- 明确的节点类型；
- 明确的场景层级；
- signal 表达事件；
- Resource 表达数据；
- Node 表达编辑器/生命周期对象；
- RefCounted 表达纯运行时对象。

不要把 Manager、Service Locator、动态方法查询当成默认方案。

## 14. 修改前必须回答三个问题

AI 在修改较大功能前，应先在内部确认：

1. 当前真正的问题是什么？
2. 最小修改是什么？
3. 是否正在引入新的状态、缓存、副作用或抽象？

如果第三项答案是“是”，必须确认它确实必要。

## 15. 完成修改后检查

提交代码前检查：

- 有没有重复逻辑？
- 有没有无意义 fallback？
- 有没有 getter 副作用？
- 有没有一个函数同时修改多个系统？
- 有没有新增但不必要的抽象？
- 有没有热循环里的昂贵操作？
- 有没有注释比实现还长？
- 有没有注释与真实代码行为不一致？
- 能否删除代码而保持同样功能？

**能用更少代码表达同样清晰的行为时，优先删除代码。**

---

## 项目代码的目标

不是：

> 尽可能通用、自动兼容所有情况。

而是：

> 在当前游戏的明确约束下，用最少、最直接、最容易调试的代码实现功能。

AI 应优先像项目维护者一样写代码，而不是像代码生成器一样覆盖所有可能性。
